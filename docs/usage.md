# Usage guide

Point Query Transformer (PET), fine-tuned to count wheat tips and pea plants from
smartphone field photos (and, via `--drone`, from linear-meter drone plot
tiles). One model per species; a fixed pipeline of four steps: prepare data,
train, evaluate, run inference, plus an optional joint visualization that
overlays both species' predictions on the same image.

This is a cleaned-up, single-configuration version of the original experiment
tree: only the retained pipeline is here (whole-image resize, no
tiling/TPC-pretraining variants, no dual-species joint model).

For data confidentiality reasons, the field images are not included in this repository.

## Structure

```
wpcount/
├── PET/                  # PET model code (fork of github.com/cxliu0/PET), fine-tuning engine
│   ├── main.py            # training entry point (CLI args, training loop, checkpointing)
│   ├── engine.py          # train_one_epoch / evaluate (loss step, val MAE+F1)
│   ├── models/             # backbone (VGG16-bn), transformer encoder/decoder, PET heads
│   ├── datasets/            # ShanghaiTech-style (SHA) dataset loader
│   └── util/misc.py
├── pet_final/             # data prep, SLURM job scripts, standalone eval/inference/viz
│   ├── prepare_pet_data.py/.sh   # annotations -> PET SHA layout
│   ├── train.sh                  # fine-tune from the crowd checkpoint
│   ├── eval.sh + eval_metrics.py # test-set metrics + per-image visualizations
│   ├── infer.py/.sh              # inference on a raw folder of images (no GT needed)
│   ├── joint_viz.py              # overlay wheat+pea eval outputs on one frame
│   ├── size_curve.sh + size_curve_aggregate.py  # val MAE vs. training-set size sweep
│   └── strip_ckpt.py             # one-time: strip a downloaded checkpoint to weights-only
├── annotations/           # your input: images/ + annotations_wheat.json + annotations_pea.json
├── annotations_drone/     # optional, same structure, used with --drone
├── all_annotations/       # working annotation pool (full photo set, not just the trained-on subset)
│   ├── annotate.py         # local Tkinter tool: annotate wheat+pea points on images/
│   ├── assign_split.py     # batch-assign train/val/test to images left at split "?"
│   ├── annotations_wheat.json
│   ├── annotations_pea.json
│   └── images/             # every collected photo, annotated or not
├── drone_extraction/      # local, optional: QGIS click capture + orthomosaic tile extraction
│   ├── qgis_click_collector.py  # paste into QGIS's Python console to record transect corners
│   ├── extract_linm.py          # warps recorded transects into GeoTIFF tiles
│   └── preview_linm.py          # sanity-check plot: draws recorded transects on the orthomosaic
├── explore_outputs.py     # local Tkinter viewer for eval/inference/joint output images
└── example_annotations.json  # minimal sample of the annotation JSON format (4 dummy images)
```

Everything under `PET/outputs/`, `pet_final/data_*/`, `pet_final/outputs_*/`,
`pet_final/pretrained/`, `PET/pretrained/`, `pet_final_out/`, and `PET_jobs/`
(per-job symlink workdirs created by `train.sh`/`infer.sh`) is generated by
the scripts below and is not included here.

## Setup

1. **Environment**, named `PET_ENV` and defined in [`environment.yml`](../environment.yml)
   (the `.sh` scripts activate it by that name by default; override with
   `--env <name>` or the `PET_ENV` shell variable to use another environment):
   ```bash
   mamba env create -f environment.yml          # create the environment once
   mamba activate PET_ENV                       # activate it in every new terminal
   mamba env update -f environment.yml --prune  # after environment.yml changes
   ```

2. **ImageNet backbone** (VGG16-bn), used to initialize the PET backbone:
   ```bash
   mkdir -p PET/pretrained
   curl -L -o PET/pretrained/vgg16_bn-6c64b313.pth \
       https://download.pytorch.org/models/vgg16_bn-6c64b313.pth
   ```

3. **Crowd-pretrained PET checkpoint** (ShanghaiTech-A), the starting point for
   fine-tuning. Download `SHA_model.pth` from the official PET repo's
   [Pretrained Models](https://github.com/cxliu0/PET#pretrained-models) table
   (direct link: [Google Drive](https://drive.google.com/file/d/1QwV8hrEDs1LQ4h1TH4KSL8tB51AImNMT/view?usp=drive_link)),
   then strip it to weights-only (drops optimizer/epoch state so training starts
   fresh at epoch 0). Google Drive needs `gdown` (not plain `curl`) to get past
   its confirmation page for files this size. Pass the file ID directly, it's
   more stable across gdown versions than the full share URL:
   ```bash
   gdown 1QwV8hrEDs1LQ4h1TH4KSL8tB51AImNMT -O SHA_model.pth
   python pet_final/strip_ckpt.py --src SHA_model.pth
   # -> pet_final/pretrained/pet_sha_model_only.pth
   ```

4. **Annotations + images**: place your data at
   ```
   annotations/
     images/                    <- all photos, wheat and pea annotations both point into this one folder
     annotations_wheat.json
     annotations_pea.json
   ```
   Each JSON is `{"<image filename>.jpg": {"points": [[x, y], ...], "split": "train"|"val"|"test"}, ...}`.
   See `example_annotations.json` at the repo root for a minimal sample with
   4 dummy images. A custom location works too: pass `--path /custom/annotations`
   to `prepare_pet_data.py`/`.sh`, as long as it has the same `images/` +
   `annotations_wheat.json` + `annotations_pea.json` structure. For drone data,
   put the same three things under `annotations_drone/` instead (`--drone` on
   `prepare_pet_data.py`/`.sh` uses that folder by default, see step 1).

   See "Annotating" and "Drone tile extraction" below for how to actually
   produce these files rather than writing them by hand.

## Annotating

`all_annotations/` is the working annotation pool, kept separate from
`annotations/`: it holds *every* collected photo (`images/`), not just the
ones already annotated and frozen into `annotations/` for the last training
run, so you can keep annotating new photos without disturbing what you've
already trained on.

Run `python all_annotations/annotate.py` (local, Tkinter, needs a display,
not for the cluster): it opens every image in `all_annotations/images/`,
preloads whatever points already exist for it in
`all_annotations/annotations_wheat.json`/`annotations_pea.json`, and lets you
place new wheat (red) and pea (blue) points on the same image (both species
can be annotated together since plots are intercropped), then saves back into
the two JSONs in place. See the module docstring for full controls (write vs
erase mode, zoom/pan, navigation).

Once you're happy with a batch of new annotations, fold
`all_annotations/annotations_wheat.json`/`annotations_pea.json` + `images/`
back into `annotations/` (or point `prepare_pet_data.py --path` straight at
`all_annotations/`) to actually train on them.

A freshly-annotated image is left at `"split": "?"`: `annotate.py` never
forces you to decide train/val/test while you're still placing points, and
`prepare_pet_data.py` silently skips `"?"` entries, so nothing breaks, they
just won't be in any split yet. **Closing `annotate.py` prints a summary,
separately for wheat and pea, of how many annotated images currently sit in
each of train/val/test/`?`** (the two species never have the same number of
annotated images, so a single combined count wouldn't mean much).

Once there are enough `"?"` images for one species, batch-assign them with:
```bash
python all_annotations/assign_split.py --wheat --train 50 --test 10 --val 10
python all_annotations/assign_split.py --pea   --train 30 --test 5  --val 5
```
`--wheat`/`--pea` is required: it runs on exactly one species' JSON at a
time, since wheat and pea have different numbers of annotated images and
therefore different-sized `"?"` pools. This sorts that species' `"?"` images
alphabetically and assigns the first `--train` of them to train, the next
`--test` to test, the next `--val` to val (the remainder stays `"?"`). Run it
again later (for either species) with more `"?"` images to top up any split.
Wheat and pea are trained as two entirely separate models on their own test
sets, so there's no requirement that a mixed image's split agree between the
two species.

`annotations_drone/` doesn't have its own `annotate.py`: it's populated once
from `wheatpea_count/annotation.json` (outside this repo) rather than
annotated live here.

## Drone tile extraction

`drone_extraction/` (local, optional) is the step that produces drone tile
images in the first place, upstream of annotation. It needs QGIS (click
collector) and GDAL (`extract_linm.py`/`preview_linm.py`), neither of which
is part of the `PET_ENV` conda env from Setup step 1.

1. **`qgis_click_collector.py`**: paste into QGIS's Python console (Plugins
   -> Python Console -> Show Editor) with the orthomosaic open (project in
   EPSG:2154). Right-click records a corner, left-click pans. Per transect:
   call `set_plot(X, Y)`, then 4 right-clicks for the "5SW" variant (TL, TR,
   BR, BL corners in that order), then 4 more for "3NE". Writes
   `drone_extraction/linm_ref.json` in real time. Other console commands:
   `remove(X, Y[, "5SW"|"3NE"])`, `undo()`, `status()`, `stop()`, `resume()`,
   `done()`; see the module docstring for the full list.

2. **`preview_linm.py`** (optional sanity check): draws every recorded
   transect as a rectangle over a downsampled render of the orthomosaic:
   ```bash
   python wpcount/drone_extraction/preview_linm.py
   ```
   Run from the MPAC root (the parent of `wpcount/`). Writes
   `drone_extraction/linm_preview.png` and opens it. Fix corners in
   `linm_ref.json` (re-run the click collector) and re-run this to check the
   fit before extracting.

3. **`extract_linm.py`**: warps each recorded transect into its own GeoTIFF
   tile via GDAL, written straight into `annotations_drone/images/`:
   ```bash
   python wpcount/drone_extraction/extract_linm.py \
       --tif   data/.../orthomosaic_geo.tif \
       --angle 45
   ```
   Also run from the MPAC root. `--angle` (`45` or `90`, required) is appended
   to each tile's filename (e.g. `79_12_5SW_45.tif`) so both flight angles of
   the same plot can coexist. `--pixel_mm` (default 2.0) sets the output
   resolution; `--force` re-extracts transects that already exist in the
   output folder (by default they're skipped).

## Pipeline

All commands run from `wpcount/`. The `.sh` scripts are SLURM jobs (`sbatch ...`);
the `.py` files can also be run directly for local debugging.

### 1. Prepare data

Resizes images so their long side = the target resolution, converts point
annotations to PET's ShanghaiTech `.mat` layout, and writes both species into
one shared directory per resolution:

```bash
sbatch pet_final/prepare_pet_data.sh                        # resolution 2048 (default)
sbatch pet_final/prepare_pet_data.sh --resolution 1500       # one resolution
sbatch pet_final/prepare_pet_data.sh --resolution 1500 2500 3000   # several in one job
sbatch pet_final/prepare_pet_data.sh --drone --resolution 2048     # drone source instead of smartphone
```

Output: `pet_final/data_<resolution>/{wheat,wheat_test,pea,pea_test}/`, each
containing `train_data/` or `test_data/` with `images/` + `ground-truth/`
(`wheat`/`pea` hold the train+val split, `wheat_test`/`pea_test` hold the
held-out test split; `val` is `test_data/` under the plain `wheat`/`pea` root,
`test` is `test_data/` under `wheat_test`/`pea_test`; this mirrors the
`"split": "train"|"val"|"test"` field in the annotation JSON).

`--drone` reads from `annotations_drone/` instead of `annotations/` (or from
`--path` if you pass one explicitly, since `--drone` only changes the *default*)
and writes to `pet_final/data_drone_<resolution>/` instead of
`pet_final/data_<resolution>/`, so smartphone and drone data never collide and
can both exist at the same resolution simultaneously.

### 2. Train

```bash
sbatch pet_final/train.sh --wheat
sbatch pet_final/train.sh --pea
sbatch pet_final/train.sh --wheat --resolution 1500
sbatch pet_final/train.sh --wheat --epochs 300 --batch_size 8 --lr 1e-4
sbatch pet_final/train.sh --wheat --drone --resolution 2048
```

`--wheat`/`--pea` selects which species to fine-tune; it is required, and mutually
exclusive (the job errors out immediately if you pass both or neither). It
picks the training data (`pet_final/data_<resolution>/wheat/` vs `.../pea/`)
and the output checkpoint directory (`pet_wheat_<resolution>` vs
`pet_pea_<resolution>`); there is no dual-species model. `--resolution`
(default 2048) must name a resolution you already prepared in step 1; it
selects which `data_<resolution>/` directory to train on and is baked into the
checkpoint directory name so different resolutions never collide.

`--drone` trains on `pet_final/data_drone_<resolution>/` instead (must have
been prepared with `prepare_pet_data.sh --drone` first) and inserts `drone_`
into the checkpoint directory name (`pet_drone_wheat_<resolution>`) and log
filename, so drone and smartphone runs for the same species/resolution never
overwrite each other.

Fine-tunes from `pet_final/pretrained/pet_sha_model_only.pth` unless `--resume
<path>` overrides it (e.g. to resume a crashed run from `checkpoint.pth`).

Checkpoint selection: every `--eval_freq` epochs (default 5), the model is
evaluated on the `val` split; whenever that epoch beats the running-best val
MAE, its weights are saved as `best_checkpoint.pth` (with that exact epoch's
`best_mae`/`best_epoch` recorded alongside them, not just a copy of the
latest `checkpoint.pth`, whose own `best_mae` field always lags one eval
behind since it's written before that epoch's val pass runs). A point-matching
F1 (at `20 * resolution/2048` px) is computed and logged at the same time for
visibility, but does not drive checkpoint selection: an F1-based criterion
was tried and produced worse count accuracy (good localization, bad
MAE/MAPE), hence MAE.

Checkpoints: `PET/outputs/SHA/pet_[drone_]<species>_<resolution>/{checkpoint.pth,best_checkpoint.pth}`
(e.g. `pet_wheat_1500`, `pet_drone_pea_2048`).

Logs: `pet_final_out/train_pet_[drone_]<species>_<resolution>_<timestamp>.out`. Learning
curve (train loss + val MAE + val F1, one plot with 3 y-axes):
`pet_final/outputs_[drone_]<species>_<resolution>/vis/learningcurve_<species>_<resolution>.png`,
the same folder where `eval.sh` (step 3, unbordered) writes its own plots. It's
(re)written every `--eval_freq` epochs, right after that epoch's val pass, not
only once training finishes, so it already exists and keeps updating while a
long/still-running job is training, and still reflects the latest epoch if the
job gets killed or preempted before `--epochs` is reached. This is the
per-epoch curve for a single training run; for a curve of final accuracy vs.
*how many training images were used*, see "Data-size learning curve" below.

### 3. Evaluate

```bash
sbatch pet_final/eval.sh --wheat
sbatch pet_final/eval.sh --pea --resolution 1500
sbatch pet_final/eval.sh --wheat --bordure          # exclude points near image edges (20px @2048, scaled)
sbatch pet_final/eval.sh --wheat --bordure 30       # explicit border width instead of the default
sbatch pet_final/eval.sh --wheat --px_wheat 25      # override the wheat matching threshold (default 20px @2048, scaled)
sbatch pet_final/eval.sh --pea   --px_pea 50        # override the pea matching threshold (default 40px @2048, scaled)
sbatch pet_final/eval.sh --wheat --drone --resolution 2048
sbatch pet_final/eval.sh --wheat --resume PET/outputs/SHA/pet_wheat_1500/best_checkpoint.pth
```

`--wheat`/`--pea` and `--resolution` work exactly as in training, and matter
for three separate reasons here:
- **Which checkpoint to load.** By default `eval.sh` loads
  `PET/outputs/SHA/pet_[drone_]<species>_<resolution>/best_checkpoint.pth`,
  i.e. it reconstructs the checkpoint path from `--wheat`/`--pea` +
  `--resolution` (+ `--drone`) exactly the way training named it. If you
  trained wheat at 1500 and then run `eval.sh --wheat` (implicit resolution
  2048), it will look for `pet_wheat_2048` and fail with "checkpoint not
  found"; pass `--resolution 1500` to match (and `--drone` if that's how it
  was trained). `--resume <path>` bypasses this lookup entirely and loads
  whatever checkpoint you point it to.
- **Which test data to evaluate on.** `pet_final/data_[drone_]<resolution>/<species>_test/`.
  It must again be a resolution (and drone-ness) you prepared in step 1.
- **Scaling `--bordure`/`--px_wheat`/`--px_pea`.** All three are defined at
  2048 and scaled by `value * resolution/2048`, so a given border width or
  matching tolerance stays a fixed *physical* margin in the original photo
  regardless of which resolution you're evaluating at.

`--wheat`/`--pea` is required and mutually exclusive here too. `--drone`
evaluates against `data_drone_<resolution>/` instead of `data_<resolution>/`;
use it whenever the checkpoint itself was trained with `--drone`. Reports,
for train/val/test: MAE, RMSE, MAPE, wMAPE, bias, R², plus point-level
precision/recall/F1 at the matching threshold, and the same negative-species
check (e.g. running the wheat model on pea-only images, expecting near-zero
predictions).

**`--px_wheat`/`--px_pea` are separate, species-specific matching
thresholds**: pea tolerates a larger localization error than wheat before a
predicted point is considered wrong, so its default is higher: `--px_wheat`
defaults to 20px @2048, `--px_pea` to 40px @2048. Only the one matching
whichever species `--wheat`/`--pea` selected for this run actually applies;
the other is simply ignored (both are always accepted so scripts calling
`eval.sh` for both species don't need per-species branching to pass one or
the other).

`--bordure`, `--px_wheat`, and `--px_pea` are all optional and independent of
each other; a bare `eval.sh --wheat` run applies neither the border nor a
non-default threshold. Each `eval.sh` call does exactly one pass (with or
without the border, never both), so getting both a bordered and unbordered
result (e.g. to compare) means running it twice, once with `--bordure` and
once without.

**`--bordure` matches first, then filters.** Greedy pred/GT matching always
runs on the full, unfiltered points; the border is applied to the *result* of
that matching, not before it. A matched (TP) pair is dropped only if **both**
its points fall inside the border. If just one does (e.g. the GT point is
inside the border but its correctly-matched prediction isn't), the pair is
kept as a normal TP and **both** points are still drawn in `preds_gt/`, even
the one sitting inside the border band. Only unmatched points (isolated
FP/FN) are filtered by the border individually. This avoids an edge case
where a real detection would otherwise get miscounted as a border-cut FP/FN
purely because the border line happened to fall between a GT point and its
matched prediction rather than around the pair as a whole.

Output: `pet_final/outputs_[drone_]<species>_<resolution>[_bordure]/`
```
  preds/       test images + predicted points
  preds_gt/    test images + predicted points + GT points
  preds_neg/   opposite-species test images + predicted points (GT=0 check)
  vis/         scatter plot (pred vs GT) + negative-prediction histogram
```
`preds/` and `preds_gt/` also contain `results.json` (`{stem: {gt, pred}}`) and
`points.json` (`{stem: {pred_pts, gt_pts}}`, used by `joint_viz.py`).

Logs: `pet_final_out/eval_pet_[drone_]<species>_<resolution>[_bordure]_<timestamp>.out`.

### 4. Inference (no ground truth needed)

Run a trained checkpoint on any folder of images, no SHA layout or annotations
required. Species and resolution are **not** passed as flags: they're read
straight from the checkpoint's path, which must follow the
`pet_[drone_]<wheat|pea>_<resolution>` convention that `train.sh` already
produces (a drone-trained checkpoint works exactly the same way, no separate
`--drone` flag needed here, as it's already encoded in the checkpoint path):

```bash
sbatch pet_final/infer.sh --images /path/to/photos --ckpt PET/outputs/SHA/pet_wheat_2048/best_checkpoint.pth
sbatch pet_final/infer.sh --images /path/to/photos --ckpt PET/outputs/SHA/pet_pea_1500/best_checkpoint.pth
sbatch pet_final/infer.sh --images /path/to/plots  --ckpt PET/outputs/SHA/pet_drone_wheat_2048/best_checkpoint.pth
```

If `--ckpt`'s path doesn't contain a `pet_wheat_<N>`, `pet_pea_<N>`,
`pet_drone_wheat_<N>`, or `pet_drone_pea_<N>` segment anywhere (e.g. a
checkpoint you renamed or moved), `infer.py` exits immediately with an error
explaining the expected convention; move/rename the containing folder to
match rather than passing species/resolution manually.

Output: `pet_final/inference/infer<timestamp>/{normal,bordures}/` (images with
drawn points + `preds.json`). `bordures/` additionally draws the border
rectangle and excludes points inside it.

Logs: `pet_final_out/infer_pet_[drone_]<species>_<resolution>_<timestamp>.out`
(species/resolution/drone-ness here are best-effort parsed by the shell script
for a readable filename; if the checkpoint path doesn't match the convention
the log is tagged `unknown` and `infer.py` itself still fails with the clear
error above).

### 5. Joint visualization (optional)

Overlays wheat + pea predictions from two separate `eval.sh` runs on the same
base image (requires `points.json` in both, i.e. run `eval.sh` for both
species at the same resolution/border setting first):

```bash
python pet_final/joint_viz.py \
    --wheat pet_final/outputs_wheat_2048/preds \
    --pea   pet_final/outputs_pea_2048/preds
```

Output: `pet_final/joint/<flat_name>/{preds,gt}/` + `joint_results.json`
(per-image wheat/pea pred/GT counts). Resolution and border width are
auto-detected from the input directory names.

### 6. Visual output explorer (optional, local)

A local (no SLURM, no GPU) Tkinter viewer for browsing everything steps 3-5
produced, not something you run on the cluster:

```bash
python explore_outputs.py
```

Run it from `wpcount/` (it resolves everything relative to its own location),
typically after syncing `pet_final/outputs_*/`, `pet_final/inference/`, and/or
`pet_final/joint/` back from the cluster to your machine. It needs a display
(Tkinter + Pillow; Pillow is already in the Setup env; Tkinter ships with
most Python installs but isn't guaranteed on a minimal/headless one, so this
is meant for your local machine, not the cluster).

It opens a two-panel window: a collapsible tree on the left of every
`pet_final/outputs_*/`, `inference/`, and `joint/` subdirectory, and an image
viewer on the right (mouse wheel or trackpad pinch to zoom, middle/right-click
drag to pan, ◀/▶ or arrow keys to step through images, buttons to copy the
current image's path or filename). Selecting a folder shows GT/pred counts
per image, read directly from whichever `results.json` (eval `preds/`,
`preds_gt/`), `joint_results.json` (joint viz), or `preds.json` (inference)
already sits in that folder: this tool only displays those files, it never
regenerates or edits them.

## Data-size learning curve

A different kind of learning curve from step 2's per-epoch one: how much does
val MAE improve as *more training images* are used, for a fixed
species/resolution? Useful to check whether more annotation effort is still
worth it or whether the model has plateaued. Trains the same model several
times at increasing training-set sizes, using fixed-seed nested subsets (the N=20
run's images are a subset of the N=40 run's, etc.) of the training images
already sitting in `pet_final/data_[drone_]<resolution>/<species>/train_data/`.
No new data directory is created, every size just uses a different number
of images from that one already-prepared folder.

```bash
sbatch pet_final/size_curve.sh --wheat
sbatch pet_final/size_curve.sh --pea --resolution 1500
sbatch pet_final/size_curve.sh --wheat --sizes 20 40 60 80 100
sbatch pet_final/size_curve.sh --wheat --drone --epochs 150
```

`--wheat`/`--pea` and `--resolution` work exactly as in step 2 (step 1's data
prep must already exist for that resolution). `--drone` trains on
`data_drone_<resolution>/` instead, same as step 2. `--sizes` (space-separated
integers) sets the training-set sizes to sweep; if omitted, it defaults to
20/40/60/80/100% of however many training images are actually available for
that species/resolution (deduplicated, so e.g. a 12-image train set doesn't
get five near-identical sizes). `--epochs` (default 150, lower than `train.sh`'s
300 since this runs `--epochs`-worth of training *per size*), `--batch_size`,
`--lr`, `--lr_backbone` apply to every size in the sweep (a size smaller than
`--batch_size` automatically uses that size as its own batch size instead).

All sizes run **sequentially inside one SLURM job** (no job-dependency
chaining). Each size is a full independent fine-tune from the same crowd
checkpoint, saved to its own checkpoint dir
(`PET/outputs/SHA/size_curve_[drone_]<species>_<resolution>_n<N>/`, with its
own per-epoch learning curve under `pet_final/outputs_..._n<N>/vis/`, same as
any other training run), so a run for one size failing or being interrupted
doesn't corrupt the others' results, and you can inspect any individual
size's own per-epoch training exactly like a normal run.

Once every size has finished, the job automatically aggregates their best val
MAE into one plot via `size_curve_aggregate.py` (only needed by hand to
re-plot an already-finished sweep). The output is **tracked in git**, unlike the
other generated-outputs folders above, since this is a small, meaningful
analysis artifact worth keeping around:
```
pet_final/size_curve/<species>_<resolution>[_drone]_<timestamp>/
  sizes.json                              <- {n_train, best_val_mae} per size
  size_curve_<species>_<resolution>.png   <- best val MAE vs. training images
```

Logs: `pet_final_out/size_curve_pet_[drone_]<species>_<resolution>_<timestamp>.out`.

## Naming conventions (recap)

Checkpoint, data, and output directory names all follow the same pattern:
**`<base>_[drone_]<species>_<resolution>[_bordure]`**, with wheat and pea
treated identically (no unmarked default for either species), and `drone_`
inserted right after the base name whenever `--drone` is passed:

| | Pattern | Example |
|---|---|---|
| Checkpoint dir | `pet_[drone_]<species>_<resolution>` | `pet_wheat_2048`, `pet_drone_pea_1500` |
| Eval/training-curve outputs | `outputs_[drone_]<species>_<resolution>[_bordure]` | `outputs_pea_1500`, `outputs_drone_wheat_2048_bordure` |
| `.out` logs | `<job>_pet_[drone_]<species>_<resolution>[_bordure]_<timestamp>.out` | `eval_pet_drone_wheat_1500_bordure_20260101_120000.out` |

`size_curve.sh` (see "Data-size learning curve") follows the same idea with
one extra token, `_n<N>` for the training-set size: the checkpoint dir uses
`size_curve_` instead of `pet_` as its base (`size_curve_wheat_2048_n80`),
while its per-epoch training-curve output folder keeps the normal `outputs_`
base with `_n<N>` appended (`outputs_wheat_2048_n80`); the size-curve name
only applies to the checkpoint, to keep it visually distinct from a normal
`train.sh` run.

**Resolution is always explicit**, including at the 2048 default, so nothing
silently gets overwritten when you sweep resolutions. `--drone` follows the
same logic: it changes the directory/log names, never overwrites the
equivalent smartphone run, and a drone and a smartphone checkpoint can coexist
at the same species + resolution.

Prepared **data** is the one exception: `data_[drone_]<resolution>/` is a
single shared directory per resolution (not per species), holding `wheat/`,
`wheat_test/`, `pea/`, `pea_test/` as equal sibling subfolders, because
`prepare_pet_data.py` processes both species in the same run (they're photos
of the same intercropped plots, just two different annotation files). Species
is still never ambiguous there, just expressed as a subfolder instead of a
directory-name token; `drone_` is the only token that appears in the dirname
itself, right after `data_`.

All of the above is deterministic from `--wheat`/`--pea` + `--resolution` +
whether `--drone`/`--bordure` was passed, with no manual bookkeeping needed to
find a given run's checkpoint or outputs (except `infer.sh`, which reads
species/resolution/drone-ness back out of the checkpoint path instead of
taking them as flags, see step 4).

## `.out` logs

All SLURM stdout/stderr is merged into `pet_final_out/<job>_<timestamp>.out`
(`#SBATCH --output`/`--error` are both `/dev/null`; each script redirects to
its own log with `exec >`). Contents:
- **prep**: per-split image/point counts for each species and resolution prepared.
- **train**: per-epoch loss + LR; every `--eval_freq` epochs, val MAE/MSE/F1/precision/recall
  and the running best; a final `TRAINING SUMMARY` block with the best MAE/epoch.
- **eval**: per-split (train/val/test) MAE/RMSE/MAPE/wMAPE/bias/R² and detection
  precision/recall/F1, plus the negative-species check.
- **infer**: per-image predicted count (+ border-filtered count).
